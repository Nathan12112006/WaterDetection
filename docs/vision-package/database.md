# 数据库与迁移

## 数据库职责

视觉服务使用 MySQL 5.7 保存视觉侧的数据：检测摘要、视觉事件、事件修订版本、outbox 投递记录以及运行审计信息。后端告警服务拥有自己的业务表（用户告警、通知、用户设备和操作审计）。双方表按服务边界隔离，跨服务数据交换通过 HTTP 事件接口完成。

调用方不依赖视觉数据库的内部表结构，应使用事件 API 和补偿游标读取事件。数据库只读访问适用于运维排查和数据分析，不作为实时告警链路。

## migrations 的作用

`migrations/` 是 Alembic 的数据库迁移模块，保存按顺序排列的、可审计的 schema 变更。每个迁移版本描述一次结构变更，例如创建 `vision_events`、`vision_event_outbox`、索引和唯一约束，并提供对应的升级（`upgrade`）与回滚（`downgrade`）操作。

迁移模块解决三个问题：

- 新环境可以从空数据库按版本建立完整结构；
- 已有环境可以只应用尚未执行的增量变更，避免手工改表造成漂移；
- 多个部署实例可以通过数据库版本号确认结构一致，并在发布或回滚时保留审计依据。

因此，`migrations/` 需要作为项目交付物保留，并纳入版本控制。生产发布时由部署流水线在启动视觉服务前执行 `alembic upgrade head`；应用代码不以 `create_all()` 作为生产建表入口。回滚应使用经过验证的迁移版本，不能直接删除业务表。

## 表与写入边界

视觉服务只写视觉侧表。事件确认与 outbox 写入在同一事务中完成，并以 `event_id + event_revision` 保证幂等；投递失败由 outbox 状态和重试时间记录承载。后端服务只写自己的业务表，通过事件接口接收视觉事件并自行去重、通知和审计。

## 运行要求

生产环境使用独立的视觉数据库账号，限制到视觉侧表和迁移所需权限；连接池、断线重连、备份、恢复和容量策略由部署运维配置。数据库不可用时，视觉服务保留内存监测能力并将故障状态暴露给健康接口，恢复连接后按照 outbox 和补偿游标恢复事件一致性。
