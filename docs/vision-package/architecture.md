# 项目架构

本文档描述视觉漏水监测服务的最终项目级架构、边界和运行协作方式，供后端、部署和运维团队进行集成设计。

## 1. 系统定位与边界

视觉服务是独立部署的 Python 服务，负责从多路视频源取得画面、执行视觉推理、依据连续帧证据确认视觉事件、保存视觉侧记录并提供画面和事件接口。

后端告警服务负责接收视觉事件，结合业务规则生成用户告警，执行用户、权限、通知渠道、通知重试和操作审计。视觉服务不直接管理用户，也不直接向手机发送业务通知。

```text
视频源 ──> 输入适配器 ──> CameraWorker（每路独立）
                              │
                              ├─> 感知分支调度
                              │     ├─ 全图目标检测
                              │     ├─ 变化区域检测
                              │     └─ water_surface 分割与风险区域分析
                              │
                              ├─> 结果归一化 ──> 事件状态机
                              │                         │
                              │                         ├─> vision_events
                              │                         └─> vision_event_outbox ──> HTTP 事件接收端
                              │
                              └─> 原始/标注帧缓存 ──> 快照 API

后端告警服务 <── HTTP 事件、补偿游标、健康状态、按需画面 ──> 视觉服务
```

## 2. 组件职责

| 组件 | 主要职责 | 隔离边界 |
|---|---|---|
| 输入适配器 | 统一读取本地文件、设备摄像头和 RTSP，并转换为标准帧 | 输入连接异常只影响所属 Worker |
| `CameraWorker` | 管理单路读取、有限帧队列、分支调度、状态指标和事件上下文 | 每路拥有独立队列、时序状态和重连退避 |
| 感知分支 | 按配置执行全图 YOLO、差分局部 YOLO、`water_surface` 分割 | 分支可独立限频；结果汇入统一格式 |
| 模型运行器 | 加载和复用模型权重，执行推理超时、设备选择和资源调度 | 支持单 GPU 复用及多 GPU 路由 |
| 风险区域分析器 | 将检测框或分割掩码映射到监测区、排除区和面积规则 | 区域配置按摄像头版本化 |
| 视觉事件状态机 | 将连续检测证据转换为 `confirmed`、`updated`、`recovered` 事件 | 状态按摄像头和事件类型独立维护 |
| 持久化与 outbox | 事务写入事件和待投递消息，记录修订、重试和错误 | 只写视觉数据库表 |
| HTTP API | 提供健康、启停、状态、画面、事件查询和补偿接口 | 接口版本以 `/api/v1` 管理 |
| 事件发布器 | 从 outbox 投递事件，按退避策略重试并保留失败记录 | 网络失败不丢失数据库中的事件记录 |
| Spring Boot 联调/后端 | 接收事件、幂等去重、生成业务告警和通知 | 不修改视觉表，不重建视觉状态机 |

## 3. 单路处理时序

1. Worker 连接视频源并进入预热，验证帧可读、模型可调用和首轮推理成功。
2. 读取线程将最新帧放入有界队列；处理线程按采样策略取帧，过载时丢弃旧帧而保留最新画面。
3. 分支调度器在规定频率执行全图、变化区域和分割推理；结果统一为检测/分割证据。
4. 风险区域规则过滤正常水面、排除区和不满足面积阈值的候选。
5. 状态机按连续帧、持续时间、置信度和恢复条件推进 `NORMAL → SUSPECTED → CONFIRMED → RECOVERY`。
6. 确认、更新和恢复事件以递增 `event_revision` 写入 `vision_events`，并在同一事务创建 outbox 消息。
7. 发布器向后端发送事件；后端按 `event_id + event_revision` 幂等处理。实时消息丢失时，后端使用补偿游标读取历史事件。

## 4. 多路与 GPU 资源模型

每路视频对应一个独立 `CameraWorker`，因此断流、推理超时或队列拥塞不会共享时序状态。模型权重由模型运行器复用，避免每路重复加载；GPU 推理通过设备路由、并发上限和批量策略控制显存，CPU 侧读取与预处理保持并行。

单 GPU 部署采用受控并发，按照摄像头优先级和分支预算调度；多 GPU 部署为 Worker 或模型实例分配 `device_id`，由调度策略实现负载均衡和故障转移。具体并发度以目标硬件压测结果写入 YAML，不由调用方临时决定。

## 5. 配置与版本

部署配置由 YAML 文件提供，环境变量只注入路径、密钥和部署地址等敏感或环境相关值。配置包含视频源、Worker 参数、分支频率、模型路径、GPU 设备、风险区域、事件规则、数据库和发布器设置。

每次模型、区域或采样策略变更生成新的 `config_revision`。Worker 在安全边界加载新版本，事件记录携带该版本，避免同一活动事件混用不同配置的证据。

## 6. 数据所有权与一致性

视觉数据库由视觉服务拥有，迁移由 Alembic 管理。事件和 outbox 使用唯一约束及事务保证“记录存在即有待投递消息”；发布器状态更新与重试次数可安全重复执行。后端数据库由后端服务拥有，双方通过版本化 HTTP 契约交换事件，不共享写权限。

## 7. 运维与可观测性

健康接口同时返回服务汇总状态和各 Worker 状态，包括最近帧、最近推理、处理/丢帧数、推理延迟、超时计数和最近错误。启动阶段的预热结果决定服务是否进入 `READY`；部分摄像头异常时保持其他 Worker 运行并标记 `DEGRADED`。

日志使用 `camera_id`、`event_id`、`event_revision` 和 `config_revision` 关联一次处理链路。快照接口读取最近缓存帧，不阻塞监测 Worker；原始画面和标注画面由调用方按需选择。

## 8. 集成顺序

部署方依次完成：准备 Python 运行时和模型依赖 → 配置 YAML 与视频源 → 初始化 MySQL 并执行迁移 → 启动视觉服务并检查预热和健康状态 → 配置后端事件接收端和补偿任务 → 联调原始/标注画面与事件幂等 → 进行断流、恢复、重启和压力演练。
